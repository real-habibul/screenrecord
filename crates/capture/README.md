# Capture backend

`list_devices` returns live WGC monitor/window identities, WASAPI input endpoints, and DirectShow webcam alternatives. Handles and device IDs are revalidated at recording start.

Apps groups eligible windows by owning PID, with `process:<pid>` group IDs and `app:<pid>:<hwnd>` window IDs. Names use the executable basename from [QueryFullProcessImageNameW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) with only `PROCESS_QUERY_LIMITED_INFORMATION`; owned handles close on every return. Denied metadata falls back to an actual window title. Existing monitor/window sources are preserved. Recording captures one selected window; audio defaults to the system mix, with an explicit application scope for Apps sources.

Apps validates current eligibility and [window ownership](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid) at selection parsing, delayed native startup, before/after creating the WGC item, and before the first frame is accepted. Resume repeats this path. Failed identities never select a replacement. Windows can recycle both PID and HWND, so these checks establish current ownership rather than an immutable historical process identity. Source-free tests cover grouping, denied metadata, canonical IDs, changed/stale owners, conversion races, and failed-start recovery after the app has exited. The only native metadata test queries the test process itself. Logs: `artifacts/apps-0.4.4/capture-tests.log` and `capture-clippy.log`. Actual Apps capture and resume remain manual validation.

`validate_source(id)` checks current source identity and physical bounds before the caller creates pending project files or changes capture controls. It opens no capture session or audio/camera device. Recorder startup and resume share its dimension checks and still revalidate after preflight; a source can disappear between checks, so later failures preserve recovery metadata conservatively.

`Recorder::start` creates pointer-free WGC capture with native H.264 encoding. Microphone and render-endpoint loopback audio use 48 kHz stereo float PCM. QPC anchors stream boundaries; consecutive packets advance by the negotiated stream's device frame positions, so timestamp jitter cannot insert silence between healthy packets. A separate cursor stream stores normalized physical coordinates, button state, visibility, and timestamps. Input is collected only after an explicit recording action and until the stop signal reaches the acquisition workers.

Application audio uses `ActivateAudioInterfaceAsync` with `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK` and `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. It targets the selected Apps window's owner PID and descendants. Audio from unrelated processes is excluded; an app with no rendering stream produces silence. It does not depend on one output endpoint. This API is available on supported Windows 11 systems. See [Microsoft's application loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/).

Application scope requires enabled audio and a canonical Apps identity. It rechecks the window owner and retained process handle before starting, then every 250 ms; a closed or changed target stops that audio worker visibly. Failed activation never selects the system mix. Event-driven capture uses 48 kHz stereo float PCM without querying unsupported virtual-endpoint buffer/period methods. Packet allocation is capped at two seconds, disk buffering at two seconds, and each drain at 256 packets. Pause, Resume, and the pre-recording trial use the same recorder path.

Activation has a five-second readiness deadline. Cancellation or timeout reports failure while the initialized worker retains its activation parameters, callback, operation, and target until Windows completes the callback. Cleanup waits at most 15 seconds after a failed readiness result, then quarantines the still-owned worker and blocks another recorder. A native call that never returns cannot be forcibly released safely; app restart may be needed. Callback lifetime follows [Microsoft's activation contract](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync).

Source-free tests cover scope dispatch, invalid/changed identities, include-tree parameters, agile callback interfaces, activation errors, cancellation, late completion ownership, packet limits, silence, QPC continuity, and final drain. No application audio was acquired during automated testing. Actual isolation from another app, browser/helper-process routing, protected content, device changes, target exit, trial-to-recording transition, and pause/resume remain manual checks. Audio produced by a separate broker outside the selected process tree is intentionally not added through a system-mix fallback.

Temporary recording tests use `RecordingSession::start_cancellable` with a separate caller token. Startup checks it between resources and while waiting for cursor readiness, native launch, and the first frame. A startup-only relay signals internal acquisition stop without changing the caller token. Cancellation returns `Recording test cancelled.` and retains late native resources through cleanup. Calls already inside a device driver or FFmpeg startup may finish or reach their existing timeout before cleanup completes; cancellation prevents progression to the next acquisition stage. Hardware-free tests cover pending launch, first-frame waits, late resource release, pre-cancel without files, and ordinary errors remaining distinct from cancellation.

A dedicated `WH_MOUSE_LL` thread starts before the first WGC frame. Its callback copies the position, QPC receipt time and left, right or middle button transition into a 512-event queue, then calls `CallNextHookEx`. It accepts mouse input from accessibility tools. The cursor worker samples movement every 8 ms. When Windows swaps the mouse buttons, the observer maps logical messages to physical left and right. Polling reads physical button state through `GetAsyncKeyState`. New samples use mask bits 1, 2 and 4 and satisfy `pressed == (buttons != 0)`.

The queue holds startup events until WGC publishes the first frame's dimensions and QPC timestamp. Earlier transitions establish which buttons were already held. The recorder saves clicks from the first frame onward. A hidden sample establishes held state at Start, Resume and reentry into the source. Coordinates enter the click track only for a visible pointer over the selected source, outside recorder controls. Window and Apps capture check the root HWND under the event point. Monitor capture includes visible applications on the display. The cursor worker checks source bounds and occlusion when it drains the queue. Rapid window moves and resizes during delivery need a manual device check.

If the hook fails to start, the queue fills, the observer exits or its state consistently disagrees with polling, the recorder switches to 8 ms button polling. Short clicks may be missed in that mode. Stop and recovery collect the notice from `cursor-warning.txt`. Cursor JSON uses a 16-million-sample limit and a one-second flush interval. Stop and Pause signal the observer, join its thread and drain accepted events up to the stop timestamp. Native cleanup retains ownership of workers that exceed its deadline.

Windows can silently remove a timed-out low-level hook without a notification API. The callback is deliberately short, and persistent state mismatch can reveal some delivery loss, but a wholly missed short down/up pair cannot always be detected. Secure desktops, elevated applications, raw-relative games, remote/input-device behavior and swapped-button configurations remain manual hardware checks. No global hook or physical input was activated by the synthetic tests. Tests cover rapid/chord edges, initial/reentry state, visibility/occlusion rules, paused/stop boundaries, final queued-edge drain, bounded overflow and journal recovery including legacy unknown-button samples.

Primary references: [LowLevelMouseProc lifetime and timeout](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc), [event screen coordinates](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct), [physical polling semantics](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate), [Microsoft PowerToys swapped-button investigation](https://github.com/microsoft/PowerToys/issues/30714), and [UnhookWindowsHookEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwindowshookex).

Webcam capture uses the supplied FFmpeg executable with DirectShow and `h264_mf`, writing fragmented MP4. Finalization remuxes compressed packets into `camera-source.mp4` without re-encoding. Screen time `t` maps to camera time `t + camera_offset_seconds`; old aligned `camera.mp4` projects retain offset zero. The journal publishes the offset before the new filename, so a failed remux cannot apply it to legacy media. Short camera tracks remain usable, with a warning; preview/export hide the camera after its EOF.

Camera input sets `use_video_device_timestamps=false` before opening DirectShow. Bundled FFmpeg 8.1.3 (`a35157abb9`) then assigns the graph reference clock to frame PTS, so slow virtual-camera delivery does not compress elapsed time into the declared frame rate. Startup verifies that chosen timestamps equal graph timestamps, waits for eight observations and encoded output, then freezes the minimum receipt-delay mapping to QPC. Remux retains these timestamps and the established offset. Graph-clock accuracy, pipe latency, and physical lip-sync still need device tests. Source timing logs are capped at 1 MiB; per-frame diagnostics are consumed without being saved. No camera frames are uploaded.

Each child process is attached to a kill-on-close Windows Job Object. Dropping a live recorder requests acquisition stop before finalizing any screen segment. Webcam stop allows progress to continue for up to ten seconds, with a two-second inactivity deadline and two-second post-completion grace. Process termination alone never proves media completion. A completed stream from a lingering terminated process must have an exact end marker, no FFmpeg error, reaped process/readers, and full decode validation before normal publication. That validation runs in the media-finalization phase, outside the 15-second native cleanup wait. Incomplete or failed media retains the recovery path. Native workers remain owned by the cleanup registry until released; another recording cannot race them.

FFmpeg finalization has a 90-second inactivity watchdog instead of a fixed total deadline. Advancing timestamps, output size, or input I/O reset it; input I/O also covers MP4 faststart copying after timestamps stop advancing. Audio acquisition hands packets to a separate disk writer through a nonblocking queue capped at 768,000 payload bytes (two seconds per track, including a packet currently being written). A full queue reports an error instead of growing or blocking WASAPI. Stop freezes the audio stream, drains pending packets, then truncates/pads the WAV at the requested end sample. Disk writes and one-second checkpoints run outside acquisition.

## Camera preview

`preview::CameraPreview::start(camera_id, ffmpeg)` opens only the caller-selected DirectShow camera. The app validates this ID against native enumeration, reserves a cancellable session before spawning, and requires an explicit Enable preview click. The preview uses the same native camera identity as recording, without WebView permission/device-ID mapping. It does not open audio, save frames/logs, or upload media.

FFmpeg writes JPEGs to a pipe at 4 fps, scaled within 480 by 270 pixels. The reader keeps one latest frame, capped at 512 KiB, and respects JPEG segment lengths and escaped entropy markers. DirectShow input buffering is capped at 16 MiB; decoding, filtering, and JPEG encoding each request one thread. The negotiated camera input mode may still run at its native resolution/frame rate, so physical-device CPU cost needs measurement. IPC snapshots clone the current frame and the app base64-encodes it for polling; there is no frame backlog.

Startup returns after process/thread creation. A watchdog terminates the process after 15 seconds without an initial frame or 5 seconds without another frame. Stop and Drop terminate the kill-on-close Job Object immediately, clear the displayed frame, and reap/join through the capture cleanup registry with a two-second caller deadline. A delayed cleanup keeps the next recording blocked. The app stops preview before starting recording and on dialog close/device change/application close; session IDs keep delayed commands from reviving or stopping a newer preview.

The synthetic `preview::tests::media_contract_preview_frames_stop_drop_and_timeout` test exercises streamed JPEGs, process termination on Stop/Drop, and timeout without opening a camera. Parser tests cover embedded marker bytes, arbitrary partial boundaries, truncation, and size limits. `tests/ui/camera-preview.spec.ts` covers explicit activation, matching native IDs, decoded JPEGs, cancellation during startup, discarded late frames, device changes, unmount, error/retry, keyboard operation, and narrow dark/light layouts. These tests do not establish physical camera availability, privacy permissions, disconnect behavior, or release-to-record latency on actual hardware.

Primary format references: [FFmpeg DirectShow input](https://github.com/FFmpeg/FFmpeg/blob/n8.1/doc/indevs.texi) and [FFmpeg image2pipe muxer](https://github.com/FFmpeg/FFmpeg/blob/n8.1/doc/muxers.texi).

## Audio analysis and microphone test

`analysis::analyze` accepts one existing audio file, its source duration, up to 512 retained source intervals, and 1 to 4096 waveform bins. It streams native-rate float PCM from a hidden FFmpeg child without creating media files or loading the recording into memory. The waveform covers the complete file timeline: bin `i` covers `[i * duration / bins, (i + 1) * duration / bins)`. Each bin contains the minimum and maximum across channels. Empty bins are zero. Recorded tracks use recording source seconds; imported music uses file seconds, mapped by the caller through the clip's source offset and timeline position.

Peak and RMS use only samples whose native timestamps fall inside the retained intervals. Empty intervals select the whole source; the app must reject a music clip with no retained overlap. Intervals do not bridge positive gaps, and overlapping tolerance samples are counted once. Native boundary indices distinguish an exact sample boundary from a positive subsample cut before accumulating statistics. Existing volume, normalization, fades, and ducking are excluded from these raw-source measurements. Recommended gain targets RMS -18 dBFS, caps the predicted raw peak at -1 dBFS, and is bounded to 0.01 through 8; silence returns 1. These are sample peak and RMS measurements, not LUFS or true-peak loudness normalization. The gain bound can prevent achieving the target on extreme sources.

Analysis memory contains fixed 64 KiB decode/read buffers, at most 4096 bins, interval indices, and one bounded progress message. FFmpeg's decoder allocations are separate. Source duration is limited to 24 hours, decoded formats to 1-8 channels and rates up to 768 kHz. Nonfinite samples, unsupported formats, and incomplete frames fail. Cancellation is polled every 25 ms and between decode blocks. A 30-second no-progress limit and 10-minute total deadline bound processing. Children use a Windows kill-on-close Job Object and bounded cleanup; user audio is read only.

`meter::MicrophoneMeter::start` is reserved for an explicit Start test action. The caller validates the selected native endpoint ID, assigns a session token, and stops the test before recording, device changes, dialog close, or app close. The worker independently rejects render endpoints. It requests shared 48 kHz stereo float WASAPI capture, publishes one latest peak/RMS snapshot per 100 ms of samples, and performs no playback, file writes, or upload. Startup is asynchronous; snapshots distinguish waiting, ready, stopped, and error states. A watchdog requests stop after 10 seconds without readiness or 30 seconds total. Five seconds without packets reports a disconnected/stalled source. Silent WASAPI packets contribute zero samples.

Stop and Drop request cancellation immediately and join owned workers with a two-second caller deadline. A blocked native driver remains owned by the cleanup registry and blocks another recording until released. This is bounded caller waiting, not forced in-process cancellation of a hung driver. No physical microphone was activated during Stage 2 verification.

Stage 2 tests cover native 44.1/48 kHz retained-interval statistics with louder deleted samples, stereo RMS, silence, gain/peak limits, finite samples, bounded waveform size, interrupted streaming, packet-sized meter windows, startup/lifetime expiry, Stop/Drop, visible worker failure, and deferred cleanup ownership. `analysis::tests::media_contract_audio_analysis_streams_native_pcm_and_cancels_owned_child` runs a synthetic WAV through actual FFmpeg and terminates a paced synthetic child. It never opens a capture device. Microphone permission handling, physical disconnect behavior, selected-device levels, and device release latency still require a manual hardware check.

Primary meter reference: [Microsoft WASAPI capture packet lifecycle and silent-buffer semantics](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer).

## Recording sessions and Pause

Version 0.4.1 bounds native screen initialization separately from first-frame readiness. An initialization timeout transfers the startup worker to the cleanup registry; a late result is stopped, and another recording/recovery remains blocked while native work is outstanding. First-frame waiting polls worker termination and preserves its error. Timeouts distinguish missing display/window frames from a delivered frame blocked in encoder setup, submission, or GPU snapshot setup. The original 15-second first-frame limit is unchanged.

`never_started_screen` is a read-only failed-start classifier for the app's pending-marker lifecycle. It accepts only explicit initial version-one session metadata or a legacy initial journal, zero screen epoch/duration, no completed segments, no final/partial screen files, and an empty segment directory. Unknown/incomplete metadata, links, missing directories, or unexpected recording parts preserve recovery. Camera and audio files are never removed or modified. The application may archive a proven empty screen attempt's pending marker separately while retaining all original files.

The two reported failed attempts had zero screen epoch and no screen segment, which places failure before the application processed a frame. The vendored free-threaded pool removes dispatcher-dependent frame delivery; native HRESULTs are now surfaced. Synthetic WARP/ownership and fault-injection tests do not establish successful physical monitor capture. A user-run monitor/window retry and pause/resume/device-release check remain required.

Version 0.4.3 records metadata-only `capture-startup-diagnostic.json` inside a failed part. It includes schema/app versions, time, selected source geometry, independent native/application checkpoints, FrameArrived and handler counts, worker completion, and the last HRESULT. It neither captures media nor overwrites an existing diagnostic. The filename does not interfere with conservative failed-start classification. A timeout before the application handler no longer claims that Windows emitted no event: it may have stalled earlier inside native frame handling. The dedicated worker also removes an unnecessary dispatcher lifetime and rolls back partially registered native resources; see the vendored patch notes for tests and primary contracts. The latest two failures were camera-disabled attempts on a monitor that had successfully recorded earlier, so webcam shutdown changes cannot explain those failures.

`session::RecordingSession` wraps native recording parts. `pause` requests acquisition stop and finalizes the active `Recorder`; no screen, camera, microphone, or system-audio worker is kept running while paused. `elapsed` freezes at the sum of saved part durations. `resume` creates a new part, revalidates the selected source/devices, and rejects changed source dimensions before device acquisition when detectable. A second check covers a resize between that precheck and the first WGC frame. Stop returns ordered `CaptureResult` values with their original part-local cursor times and camera offsets. The app/render layer joins them and adds cumulative offsets.

`session-journal.json` is flushed before each part starts. Its exact relative names are `part-00000` through at most `part-00511`; each part contains the normal capture recovery files below. The bounded journal rejects traversal, alternate stream paths, links, junctions, and unsupported geometry. Sessions allow up to 512 parts and eight recorded hours; the caller must poll `health` and stop when the duration limit is reported. Failed Pause/Resume leaves the session paused and requires Stop/recovery rather than continuing over uncertain media. Drop stops an active native part through the existing cleanup registry.

`recover_session` checks deferred cleanup for every part before reading media, then recovers usable compatible parts in order. Missing, damaged, or differently sized parts remain on disk and are omitted only with an explicit root `recovery-warning.txt`; no usable parts is an error. Partial camera/audio warnings are also copied to the session root during normal finalization. The session layer never deletes or rewrites original parts to remove paused time. Legacy single-part projects still use `recover`.

During recording, the same camera FFmpeg process writes both fragmented H.264 MP4 and JPEG thumbnails. It opens the DirectShow device once. JPEG stdout is continuously drained into one latest frame, at 4 fps within 480x270 pixels and at most 512 KiB; progress/source-clock diagnostics use stderr. Stopping suppresses thumbnail publication while draining encoder shutdown bytes, so a closed thumbnail pipe cannot interrupt MP4 finalization. A 5-second thumbnail stall marks the camera unhealthy and terminates its owned process. Session snapshots clear while paused; `generation` changes on each new part so the UI can reject stale JPEGs. Cursor samples over this app's windows are hidden and do not generate recorded clicks, including controls excluded from screen capture.

Stage 3 offline checks cover Pause releasing all fake acquisition, frozen elapsed time, idempotent Pause, ordered untouched cursor timestamps, failed finalization/resume, Drop, part/time limits, malicious paths, a real Windows junction, changed-size recovery, and an owned stalled-camera process. `media_contract_recording_camera_encodes_and_streams_bounded_latest_thumbnail` records synthetic video and checks concurrent JPEG delivery, frame bounds, Stop cleanup, and complete MP4 decode. `media_contract_session_recovery_keeps_ordered_parts_and_reports_failed_resume` rebuilds synthetic parts around a missing part and verifies warnings, decode, order, and unchanged original bytes. No physical camera, microphone, screen, or native UI was activated for these checks. Physical pause/reopen latency, device exclusivity/disconnects, window resizing, control exclusion, and camera lip-sync still need manual device validation.

## Local mask tracking

`tracking::track` reads an existing source video and returns original-source `MaskKeyframe` positions. The caller supplies the project dimensions, a normalized rectangle, a 0.01-300 second source range, a cancellation token, and a progress callback. The dimensions must match the probed stream. Input files are read only. The caller owns project validation, exclusive job registration, manual correction history, and the required review before export.

The decoder samples the frame active at `start + n / 10` seconds, with source-end trimming before causal frame-rate conversion. A frame whose presentation begins after the requested sample cannot become its template. Analysis uses grayscale frames with a longest edge of at most 640 pixels. The fixed initial template has at most 64 coarse and 256 fine samples. Each step searches translations within 24 analysis pixels, checks at most 2401 positions, and refines 32 candidates. Correlation below 0.94, a competing match within 0.035, low texture, a small target below 8x8 analysis pixels, or an out-of-frame result produces a full-screen `lost` key. It stops immediately and never silently reacquires the target. A manual correction must start a new forward run.

This is fixed-size translation tracking, not object recognition. Color-only distinctions with equal grayscale luminance, scale/rotation changes, occlusion, fast motion, similar targets, and detail lost during downscaling can defeat it. Ten samples per second and the last sampled position cannot establish exact motion between samples or in the final sub-100ms tail. Confidence is a correlation score, not a probability or proof of redaction. The editor's conservative rectangle evaluation and mandatory review remain necessary.

Memory consists of one grayscale frame (at most 409600 bytes), a 64 KiB pipe buffer, at most 320 template samples, 32 candidate matches, at most 3000 keyframes, and one completion message. FFmpeg decoder allocations are separate. There is no raw-frame queue or media output. Original inputs are limited to 8192 pixels per side and 33554432 pixels total. Probe output is capped at 16 KiB; probe/decoder stalls have a 15-second deadline, with a 15-minute total processing limit. Cancellation is checked every 25 ms and every search row. Hidden subprocesses run in a kill-on-close Windows Job Object; cancellation, reader error, early loss, and timeout terminate and reap them with bounded caller cleanup.

Stage 6 offline tests include translation in both directions and at source edges, constant/ambiguous texture, brightness changes, inverted texture, occlusion followed by reappearance, truncated input, invalid ranges/geometry, blocked-decoder cancellation, watchdog expiry, and reader failure. Four `tracking::tests::media_contract_*` cases exercise real FFmpeg using generated PNG/MOV sources: fractional and nonzero source time, CFR and sparse/VFR red/blue future-frame sentinels, occlusion latch, dimension mismatch, byte-for-byte source immutability, and 1080p downscaling. On this development machine, the debug 10-second 1920x1080 fixture produced 100 correct 640x360 analysis positions in 0.5171 seconds. This is synthetic evidence, not hardware capture or arbitrary-content accuracy coverage.

Primary decoder reference: [FFmpeg n8.1.3 causal frame-rate timestamp rounding and frame selection](https://github.com/FFmpeg/FFmpeg/blob/n8.1.3/libavfilter/vf_fps.c).

## Per-part recovery files

- `capture-journal.json`: version, geometry, frame rate, QPC epochs, completed segment names/durations, and optional camera source offset. Replaced atomically after each finalized segment.
- `segments/screen-NNNNN.mp4`: native H.264 chunks, finalized approximately every 12 seconds. A static-frame clock keeps progress and segment recovery working when the source stops producing changed frames.
- `cursor.ndjson`: cursor metadata, flushed once per second.
- `microphone.wav` and `system.wav`: headers refreshed every second so completed PCM can be read after a process crash. Files use ordinary RIFF below 4 GiB and switch in place to RF64 with 64-bit sample counts for longer recordings.
- `camera.raw.mp4`: original fragmented camera stream; `camera-source.mp4` is the remuxed source with a journal offset. `camera.mp4` denotes a legacy aligned track only.

`recover` decodes existing final videos before accepting them, checks dimensions/duration, and validates finalized chunks before rebuilding. Invalid finals are preserved under `*.invalid-NNNN.mp4`; if a chunk is damaged, recovery returns the consecutive decodable prefix and preserves all originals. WAV validation checks the format and declared PCM length against the physical file. Missing/corrupt optional tracks are reported in `recovery-warning.txt` while good screen content is retained. The in-progress native MP4 chunk is not recoverable after an abrupt crash, so recovery can lose approximately the latest 12 seconds. Recovery rejects journal path traversal, reparse escapes, oversized cursor lines, and more than 16 million cursor samples.

The recorder captures SDR BGRA frames. HDR tone mapping is not implemented. Source resize retains the original recording canvas and crops/pads subsequent frames; cursor coordinates use that fixed canvas and hide outside visible source/canvas bounds. Dense cursor samples are retained because removing stationary samples changes the editor's smoothing curve. Capture stops with a clear error at the same 16-million-sample limit as project storage.

The last frame is retained in GPU memory and read back on stop or when the source has supplied no new frame for half a second. Its render-target view, staging texture, and CPU readback buffer are reused. The vendored encoder bounds queued video payloads to two frames; each queued GPU frame owns a separate texture, with producer/consumer frames and native media resources allocated additionally. Completed or failed encoder workers interrupt queue waits and preserve their errors. Finish and Drop close the channels so queued frames drain before EOS. A native encoder that remains alive but stalled still requires cleanup quarantine; native threads are not forcibly terminated.

Native cleanup initializes a WinRT MTA before taking ownership of deferred capture finalizers, and keeps that apartment initialized through their destruction. Late startup, already-finished worker cleanup, normal stop, and static-frame submission use this initialization because encoder cleanup calls WinRT event-removal methods. If initialization fails, pending resources and their cleanup lock remain quarantined. Tests verify initialized work/destruction and injected initialization failure without opening devices. This follows the [RoInitialize thread contract](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-roinitialize).

## Verification

### Persistent audio analysis

`analysis::analyze_cached` keeps the existing analysis response and cancellation token. Pass the validated project directory's `.audio-analysis` child and `AnalysisCachePolicy::Reuse` for reopen/trim/normalization, or `Refresh` for an explicit Analyze action. Only completed float32 RIFF/RF64 WAVs use the direct index; other supported formats retain the bounded FFmpeg decoder. A missing or unwritable cache never prevents a fresh analysis.

The index stores 4096-frame block extrema and sum of squares, plus at most 4096 waveform bins over the source timeline. Retained intervals use native half-open sample boundaries. Complete blocks contribute cached statistics; partial blocks are read from the original PCM, so a removed loud sample cannot change the recommended gain. Silence remains unity and automatic gain stays within 0.01-2.0. Manual gain and edit envelopes do not enter these raw statistics.

Each read holds the source open with read-only sharing, rejecting simultaneous write/delete access. Cache identity includes Windows volume/file ID, file length, creation/write/change times, PCM layout, requested duration/bin count, and a 64 KiB prefix hash. Identity is checked again before returning. Replacing a file or editing it while restoring its write time invalidates the cache. This relies on normal filesystem metadata updates; the checksum is corruption detection, not authentication against an actor who can rewrite both source metadata and cache contents. Explicit Refresh always rescans the original.

Cache loads check version, exact length, bounded counts, finite statistics, and SHA-256 integrity before use. Invalid caches are recreated atomically through a synced temporary file. Source files are never written. Cache/project handles reject reparse points and remain held during writes; entries that are links or directories are preserved. Cache files are capped at 64 MiB, with 128 entries and 256 MiB of recognized entries per project. No recursive cleanup is performed. A one-hour 48 kHz stereo index uses about 1.4 MB; retained-range reads add at most two partial blocks per interval. Cancellation is checked between bounded reads, but Windows filesystem I/O stalled inside the kernel is not forcibly interrupted.

Source identity follows the Microsoft [file ID contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [file timestamp fields](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info), and [CreateFile sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

The ignored `analysis::cache::tests::benchmark_one_hour_cache` test generates one hour of synthetic 48 kHz stereo PCM in C: temporary storage, then compares the old decoder with persisted cache queries in fresh child processes. Run it with `--release --ignored --exact --nocapture`. It alternates three repetitions of full reopen and changed-trim requests, verifies matching waveform/peak/RMS/gain, and removes its owned source/cache fixture afterward. Reported source/cache read counters are logical reads, not physical disk traffic; fixture generation and compilation are excluded. Ordinary unit tests cover fractional 44.1/48 kHz boundaries, changed/replaced media, corruption, cancellation, junctions, RF64, and unavailable cache storage. The separately ignored PCM16 fallback test invokes FFmpeg only on synthetic audio.

Measured on the development machine on 2026-11-20 with warm filesystem caches: initial index creation took 2485.52 ms. Median analysis latency over three alternating fresh-process trials was 2515.71 ms before versus 3.54 ms cached for reopen, and 2527.58 ms before versus 3.05 ms cached for changed trim. The index occupied 1,416,077 bytes for a 1,382,400,044-byte source. Process-launch-inclusive cached medians were 55.37/54.87 ms, including the test supervisor's 25 ms polling interval. These are backend measurements, not whole-UI startup or cold-disk claims. The JSON, log, and preserved test-harness failure are in `artifacts/editor-0.7.0/audio-cache-one-hour*`; the final capture suite passed 132 tests, plus two explicitly selected analysis media tests and the one-hour benchmark. No physical capture devices were used.
