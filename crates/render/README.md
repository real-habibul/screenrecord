# Screenrecord rendering

`export` validates a saved project, composes its edit through FFmpeg, verifies H.264 dimensions, exact frame count, frame rate, duration, and required AAC audio, then publishes the MP4 without replacing an existing file. Input media remains unchanged. `probe_media` uses the ffprobe executable next to FFmpeg, with PATH as a development fallback.

Composition runs on the CPU with two FFmpeg filter threads. Video is rendered in chunks of at most 900 frames, then concatenated without re-encoding. Each retained source interval is mixed to stereo 48 kHz float PCM; the final mux concatenates those samples, applies the limiter continuously, and encodes AAC once. Encoding probes NVIDIA, Intel, AMD, then Windows Media Foundation hardware encoders at the actual output dimensions and frame rate. A diagnosed hardware encoder failure retries all video chunks through Media Foundation software encoding; input, filter, storage, cancellation, and watchdog errors do not trigger that retry. Development builds may use libx264 only if Media Foundation software is unavailable. The packaged LGPL runtime does not require libx264.

## Pause and resume assembly

`assemble_recording(&[RecordingPart], project_directory, ffmpeg, cancel, progress)` accepts finalized, ordered capture parts and returns `AssembledRecording` with media paths, geometry, logical duration, camera availability, and `part_offsets`. The app can publish a single part directly. Assembly accepts at most 512 parts, requires matching initial screen dimensions/frame rate, and confines every input to the project folder without symlinks or reparse points. Recording stops at eight hours; assembly and export accept the shared sixty-second recovery allowance so automatic-stop latency does not make a session unusable.

Logical duration is the sum of active part durations. Part offsets remain unrounded for cursor data. Video frame counts and audio sample counts use differences of cumulative ceilings at the requested fps and 48 kHz; physical media may extend less than one frame/sample past the logical end. Native audio endpoints are clipped before resampling, and missing microphone/system parts become silence. Decimal arithmetic at an otherwise exact grid boundary does not skip the first native sample. Paused time never enters the assembled timeline.

Compatible H.264 screens are concatenated without re-encoding after checking codec configuration hashes, profile, level, pixel format, time base, frame counts, durations, and every packet's integer PTS/DTS/duration and first keyframe. Input files are linked read-only into staging with generated names. Unsupported linking, fractional boundaries, VFR timestamps, or incompatible streams use the normalizing encoder path. Native journal durations can be fractional, so the copy path is an optimization, not a promise that every native recording avoids encoding.

Webcam parts use their individual offsets and actual first/last presentation times, normalized to the first camera's canvas. The assembled camera has offset zero and includes black filler for unavailable time. `cameraIntervals` restricts overlay visibility to actual source-time availability; preview/export hide the filler. Missing parts, early camera EOF, and delayed first frames remain hidden. Original part media is immutable.

All outputs are built and checked inside a unique staging directory. Final media is flushed, then Windows `MoveFileExW` publishes a unique `assembled-*` directory without replacing an existing destination. Failure or cancellation before publication removes only owned staging. The app saves the returned paths atomically in the project; a retry creates another unique result and never overwrites an earlier publication. Camera and audio normalization require temporary media and time proportional to retained duration.

Synthetic tests verify three fractional parts totaling 2.041 seconds produce 62 video frames and 97,968 stereo samples per recorded audio track. They check missing-track silence, post-stop sample exclusion, camera offsets/early EOF/startup gaps, final exported overlay pixels, unchanged originals, cancellation, geometry rejection, no-replace publication, and independent retry destinations. A compatible CFR fixture verifies unchanged compressed picture payloads; container remuxing may change parameter-set/SEI metadata without re-encoding pictures.

On this development machine with the bundled runtime and NVIDIA encoding, 60 seconds of 1920x1080 at 60 fps, a 1280x720 webcam source, and microphone/system audio finalized in 7.4756 seconds for two compatible 30-second CFR parts. Fractional 29.991/30.009-second parts, which require screen normalization, finalized in 13.6090 seconds. Both measurements exclude fixture creation, include camera alignment and both PCM tracks, verify 3,600 output frames and 2,880,000 stereo samples per audio track, and fully decode the output. They are synthetic measurements, not native-device or hour-long coverage. Reproduce with `cargo test -p screenrecord-render measure_sixty_second -- --ignored --nocapture --test-threads=1`.

## Split, cut, and ripple delete

Schema 4 `videoClips` contains chronological retained source ranges. Empty clips preserve the legacy trim. Export intersects clips with trim and merges exactly adjacent ranges, so splitting without removing time does not reset audio or change the source sampling grid. Frame and audio sample boundaries use the ceiling of cumulative output time times the rate; rounding is never accumulated per clip. Motion, cursor, masks, captions, camera offset, music placement, and music fades continue to use original source time.

Screen and camera use a microsecond filter time base and causal frame sampling (`fps:round=up`). Source-end trimming prevents an input frame after a retained interval from appearing at its fractional final frame. The last permitted screen frame is held to fill the output grid. Camera padding is used only when the camera source actually reaches the retained endpoint; an earlier real camera EOF still hides the overlay.

Captions without word timings are omitted when a cut removes any declared coverage. Timed captions retain only words whose entire intervals survive trim and cuts, then rebuild their displayed text and coverage through core `projected_subtitle`. Original cue data remains intact. Explicit `sourceRanges` allow imported captions to cover several retained spans while staying hidden in their gaps. Glyph-only PNG generation stays independent of the EDL, so cached rasters remain valid through unsaved cuts and undo. SRT and editor visibility use the same core projection.

Audio preparation opens at most the existing 34 tracks for one retained interval at a time. Temporary PCM costs 384,000 bytes per retained audio second (about 1.38 GB per hour), in addition to video chunks and the final MP4. RF64 handles long temporary WAV files. Concatenation timestamps use differences of cumulative microsecond boundaries; final audio timestamps are rebuilt from sample counts to avoid accumulating timestamp rounding at many cuts. Cancellation removes the owned temporary directory and never modifies original media or an existing output.

Audio is clipped at native integer sample timestamps before resampling. Both endpoints select the first native sample whose timestamp is at least the endpoint, without multiplying and blindly rounding floating-point decimal boundaries. Removed samples cannot enter the resampler's filter history. This differs from video: the source frame already visible at a retained start remains valid until its next presentation timestamp. Real 44.1 kHz and 48 kHz WAV sentinel tests cover fractional endpoints, nonzero coarse seeks, and padding on the cumulative 48 kHz grid.

## Normalization and audio ducking

Microphone and system normalization gains are multiplied by their respective user volumes. The original media and the stored volume remain unchanged. Source analysis and recommended gain calculation belong to the capture/core integration; rendering applies the saved gains without analyzing or normalizing again.

Ducking uses only microphone samples after microphone volume, normalization and volume keyframes. Music clip volume and fades, system volume and source gain, and each bus's volume keyframes are applied first. At 48 kHz, the detector uses stereo mean power `(L*L+R*R)/2`, smoothed exponentially with a 10 ms attack and 150 ms release. Activity rises linearly with RMS amplitude from 0.01 (-40 dBFS) to `10^(-30/20)` (-30 dBFS). The target gain is `1 - activity * (1 - 10^(-amountDb/20))`, smoothed with a 10 ms attack and 250 ms release. Each recurrence is `target + (previous - target) * exp(-1/(48000*timeConstant))`. Detector/gain state uses float64; bus input and mixed output use float32. `ducking.enabled` applies this gain to music; `ducking.systemEnabled` independently applies it to computer audio. Microphone always passes through, then the existing limiter processes the complete mix once. Old projects default `systemEnabled` to false and retain music-only behavior.

When ducking is active with microphone and an enabled target, FFmpeg streams three explicitly mapped stereo buses. Rust consumes 4096-frame blocks, writes stereo float PCM, and preserves detector state across all retained intervals. The PCM arrays total 128 KiB plus bounded I/O buffers; there is no six-channel temporary file. Each retained source interval has one decoder, avoiding resampler resets at artificial processing boundaries. Deleted microphone samples cannot influence later targets. Final AAC encoding occurs once. Without active volume envelopes, missing/muted microphone or no enabled target in retained output uses the ordinary mix path. Preview uses the same DSP and shared reference fixture, preserves state at automatic cut jumps, freezes it while cut gates are closed, and resets on explicit playback transitions.

The shared fixture in `testdata/ducking-reference.json` covers 96,000 samples with 38 output and internal-state checkpoints. Rust and JavaScript compare float32 output within 1e-7 and float64 state within 1e-12. Generated-media tests verify normalization, asymmetric stereo bus identity, music fades, retained-time detector continuity, removed-only microphone speech, missing-microphone bypass, arbitrary seven-byte pipe reads, invalid/short/extra PCM, full MP4 decoding, and cancellation. The 81,600-frame media fixture differed from an independent PCM reference by at most 7.45e-9; fragmented pipe reads produced identical output. Its encoded AAC RMSE was 0.00034683.

System-target tests cover computer audio without music, unaffected music, and both targets. Their retained-output PCM agrees with the legacy routed-bus reference within 1.49e-8, including seven-byte reads and cut transitions. Standard and WhatsApp MP4 tests force seven-frame video chunks and compare every decoded AAC sample with an independent encode of verified post-duck PCM at the appropriate bitrate. They also verify missing/muted sources and a target wholly removed by cuts bypass processing.

With the bundled runtime on this development machine, `cargo test -p screenrecord-render a_minute_of_ducking -- --nocapture` decoded and processed 60 seconds of six-bus audio in 1.0430 seconds with debug Rust, writing exactly 2,880,000 stereo frames (23,040,000 bytes). This measures the audio path alone. Run `cargo test -p screenrecord-render ducking -- --nocapture --test-threads=1` for DSP and generated-media coverage, and `cargo test -p screenrecord-render audio_stream -- --nocapture` for blocked-consumer cancellation and immediate consumer-error handling.

## Source volume keyframes

Volume keyframes are independent amplitude multipliers for microphone, computer audio and the complete music bus. Empty curves mean 1; nonempty curves hold their endpoints and interpolate linearly in original source seconds. Static gain, volume and clip fades run first, then the envelope, then ducking and the existing final limiter. A muted source stays muted. Standard and WhatsApp use the same PCM path, including compact size retries.

The renderer compiles at most 2048 numeric points per bus once, discarding identifiers from the processing table. At each retained interval it seeks the curve with a binary search, then advances an index as samples arrive. Time comes from the interval's cumulative 48 kHz grid correction plus the local sample index, so cuts neither shift keyframes nor advance the detector through removed audio. The largest numeric table is 144 KiB; the existing 128 KiB PCM arrays and bounded I/O buffers are unchanged. Empty/all-unity curves, muted or absent sources, and curves that differ from unity only in removed source ranges bypass envelope processing. Automation alone still uses the three-bus stream when ducking is off.

Run `cargo test -p screenrecord-render envelopes --locked -- --nocapture --test-threads=1` with the bundled runtime. Generated media checks all three curves before ducking, fractional cuts, overlapping music fades, adjacent splits, fragmented pipe reads, legacy bypass and cancellation. Both MP4 presets compare every decoded AAC sample with an independent encode of verified PCM using one limiter. `measure_a_minute_of_volume_envelopes_with_maximum_key_counts` is an explicit ignored audio-path benchmark, comparable to `a_minute_of_ducking_streams_with_exact_sample_count_and_bounded_buffers`.

## Edit coordinates

Source positions and crop rectangles are normalized to the original screen recording. The canvas uses the selected aspect ratio. Export resolution selects the shorter canvas edge; 1080p portrait is 1080 x 1920, 1080p square is 1080 x 1080. Padding and corner radius are reference pixels at a 1080-pixel short edge. In the default bubble layout, camera x/y specify its top-left corner as canvas fractions; its width is a fraction of canvas width, clamped to fit while preserving its aspect ratio. Circle mode takes a centered square crop from the webcam.

Camera fullscreen omits the screen composition for the entire timeline, including when the camera is disabled, missing, before its first frame, between availability intervals, or after EOF. Those times show the chosen background. Split puts the screen left and camera right on landscape/square canvases, or screen above camera on portrait canvases. Camera width becomes its share of the usable split dimension. The gap is the smaller of padding and 24 reference pixels, scaled to resolution and rounded to even pixels. The screen fits inside its pane; camera media uses a centered integer crop to cover its pane. Fullscreen and split use the canvas corner radius and ignore the bubble shape. Mirror applies to every layout. The split pane remains reserved when the camera is unavailable.

`math::layout`, `camera_rect`, and `camera_crop` define the shared preview/export geometry. Source masks, cursor, and zoom are composed inside the fitted screen pane; subtitles remain on the final canvas. Camera-free chunks bypass the camera filter branch, and looped mask images have the chunk duration, preventing an empty camera stream from keeping its alpha mask alive indefinitely. Generated-media tests in `camera_layout_tests.rs` cover landscape/portrait, camera mirror/cover/corners, source masks and cursor under crop/zoom, background-only gaps/EOF, disabled/missing camera, nonzero first PTS and offset, captions after camera EOF, and unchanged original files. Run them with `cargo test -p screenrecord-render camera_layouts -- --nocapture --test-threads=1` and `SCREENRECORD_FFMPEG` pointing to the bundled runtime.

Zoom uses 350 ms smoothstep ramps, shortened for segments shorter than 700 ms. Cursor-follow and fixed centers are clamped to the selected crop. Crop dimensions use even source pixels before scaling. Cursor smoothing uses a time-dependent exponential filter with a maximum 120 ms time constant and resets after a 500 ms gap. The drawn cursor is a fixed pointer shape; original Windows cursor shapes are not represented by the current project schema.

The pointer hotspot is at 8% of sprite width and 5% of sprite height. Its nominal height is 28 reference pixels multiplied by cursor size. Cursor movement and viewport changes are emitted at the selected export frame rate. Each chunk has at most 900 command intervals and a 256 KiB command-file limit; that file is replaced before the next chunk. An export can contain eight hours plus the sixty-second recovery allowance and 2048 chunks, with an 8192-pixel canvas limit. Seeking retains the preceding keyframe and a one-second preroll, preserving held frames in sparse input. Source timestamps are rebased onto the shared output frame grid. Webcam time is screen time plus the project's camera offset; the overlay disappears when webcam frames end or its availability interval is inactive.

Audio volumes are applied before an unnormalized mix. The limiter uses a 0.95 peak limit, 5 ms attack, 50 ms release, no adaptive release, no makeup gain, and compensated lookahead latency. Audio below the limit retains unity gain.

## Fit, reframe, and video background

Fit keeps the source crop's existing fitted pane. Fill covers the pane using an integer source viewport, without sampling outside the manual crop. Source-time reframe keys interpolate their original-screen focus and scale linearly, holding the first and last keys outside their range. Their focus replaces the cursor/fixed zoom center; their scale multiplies the existing eased zoom. Empty keys preserve the previous framing. `testdata/reframe-reference.json` supplies 34 independently calculated geometry cases shared with preview.

Video background samples a centered cover rectangle contained within that same final viewport. Both foreground and background branch from the same frame after all active redactions. Each crop has its own command file and advances only on its own input frame. The combined command files retain the 256 KiB limit per chunk and the 900-frame chunk limit. Separate crops on the original, already-redacted frame avoid stale downstream input dimensions in the bundled [FFmpeg crop filter](https://github.com/FFmpeg/FFmpeg/blob/n8.1.1/libavfilter/vf_crop.c). Cover dimensions round down to integer pixels, retaining at least one owned pixel on thin viewports.

The background is scaled directly to a scratch image with each side between 2 and 960 pixels, blurred in planar RGB with three Gaussian passes, and scaled to the canvas. Horizontal and vertical sigma account for scratch rounding and the export resolution. The [FFmpeg Gaussian filter](https://github.com/FFmpeg/FFmpeg/blob/n8.1.1/libavfilter/vf_gblur.c) supplies boundary extension; RGB composition keeps the background opaque. No oversized cover image is allocated for thin viewports. Cursor, camera, and subtitle layers are added once, after the background branch. Camera-only always uses the solid background, including unavailable camera intervals.

The generated-media background tests exercise one-pixel/odd crops at blur 4 and 64, alternating source-time focus on every frame across fractional cuts, static and tracked masks, full-black lost tracking, unchanged source media, identical decoded AAC, and cancellation. The 31-frame alternating fixture produced mean RGB difference 0.012 between 7-frame and normal chunks. Two exports and their verification took 6.945 seconds in the focused test run; that includes process startup and decoding, not a sustained encoding benchmark. Its 540x960 blur scratch and motion files were bounded, with 1,304 combined command bytes in the largest 7-frame chunk. Evidence is in `artifacts/vertical-0.5.0/render-stage3-focused-final.log`.

Camera availability, first PTS, and EOF gates use causal integer output-frame bounds. The regression checks every frame of both solid and blurred camera-only exports at 7-frame and normal chunk sizes: interval `[0.2,0.4)` at 30 fps displays frames 6 through 11 and hides frame 12. This avoids rounding a chunk-relative decimal timestamp into the following unavailable frame.

After all RGB composition, encoded export pixels use an explicit limited-range BT.709 conversion with matching matrix, primaries, transfer, and range metadata. This prevents hardware/software encoder selection from changing decoded colors through conflicting default matrix tags. The source recordings and copy-only assembly paths are unchanged. The [scale filter output matrix](https://ffmpeg.org/ffmpeg-filters.html#scale-1) is specified explicitly rather than inferred from pixel format. Generated-media tests decode nine primary/grayscale bars on available hardware and software encoders and verify all four color tags; `render-stage3-color-diagnostic.json` records the original AMF/software-MF mismatch.

The independent coordinate-gradient test checks all 30 RGB composition frames before YUV420 conversion against the original source-time equations with the unchanged five-unit RGB tolerance. Its measured maximum is 2.350. Encoded H.264 is separately compared with that RGB reference on every frame, with mean error below 2 and maximum channel error at most 8; the focused run measured maximum frame mean 1.533 and channel maximum 8. This separates framing errors from chroma subsampling and codec quantization. Whole/chunk video parity, identical decoded AAC, and unchanged originals remain required. NVIDIA, AMD AMF, and software Media Foundation primary/grayscale tests each measured channel error at most 4 with matching color tags.

## Music, subtitles, and privacy regions

`subtitle_preview(project, cue_id, word_index, ffmpeg, cancel)` renders the supplied cue's glyphs without applying saved cuts or timing. The caller supplies an already projected cue. An optional word index colors only that word when `highlightWords` is enabled; absent indices and gaps between words use the base color. Invalid indices are rejected. Raster cache identity depends on cue text, word text segmentation, selected word, style, and output dimensions, not cue timing. Full-canvas PNGs remain subject to the existing 16 MiB output limit and cancellation cleanup.

`subtitle_previews(project, cue_id, word_indices, ffmpeg, cancel)` renders 1-8 ordered appearances in one FFmpeg process. A one-fps ASS sequence produces separate PNGs in an owned temporary directory; no atlas or decoded image collection is returned. PNG encoding uses one thread. The result is limited to 16 MiB per PNG and 64 MiB compressed total, with cancellation checks before and after the subprocess and between file reads. The single-preview API delegates to a one-item batch. Callers can cache upcoming word appearances without changing the single-image frontend API.

Export uses the same escaped ASS text and color-only tags. It writes events at coverage and word boundaries on the output frame grid, including after nonzero chunk starts. It generates no per-word PNG files for MP4 export. Unicode, literal ASS-like text, wrapped lines, word boundaries, and chunk starts are covered by exact RGBA preview/export comparisons; all tested highlight variants preserve identical alpha and layout. The generated H.264 fixture has a caption-region RGB mean absolute error of 0.80564 on the 0-255 scale. On this machine, five sequential 1080p appearances took 1.6249 seconds; a five-item batch took 0.2082 seconds (24.02 appearances/second), and an eight-word batch took 0.2849 seconds (28.08/second), returning 237,471 compressed bytes. Both batch sizes match the single-render RGBA pixels exactly. These measurements exclude PNG decoding in the UI. Run `cargo test -p screenrecord-render subtitle_words -- --nocapture --test-threads=1` with `SCREENRECORD_FFMPEG` pointing to the bundled runtime.

Music clips use recording time, independent of the export trim. A clip at `start` plays source time `sourceStart + t - start`; its linear fades stay anchored to the original clip edges when the export starts or ends inside a fade. Clips are trimmed and delayed on the 48 kHz sample grid, mixed with microphone/system audio, then passed through the same limiter. Mono sources are copied to both stereo channels without an implicit gain reduction. Export checks the actual source audio duration before accepting its trim.

Privacy rectangles use floor(left/top), ceil(right/bottom) source pixels. Regions are active on `[start,end)`, before crop, zoom, cursor redraw, camera, and subtitles. Solid mode fills opaque black. Blur crops the current source rectangle, applies `gblur` with sigma equal to strength and three passes, then overlays the patch without changing pixels outside the rectangle. Overlapping regions follow array order. Chunk boundaries also include region start/end frames, keeping the active filter count bounded by the core limit of 16. Browser Gaussian blur kernels can differ; source coordinates, edge extension, activation, and operation order remain the shared preview contract. Solid coverage is available when obscuring every source pixel is required.

Tracked masks use the core `redaction_rectangle_at` evaluator at each output frame's original source time, including after cuts. Ordinary spans cover the union of their endpoint rectangles. A following manual correction holds the previous rectangle until that correction's exact time. A lost endpoint closes the preceding span and remains opaque full-source black until a manual keyframe. The final normal keyframe holds to the region end. Tracking is approximate, and any retained tracked region must be marked reviewed before the public export API proceeds.

Tracked blur uses a fixed patch size computed once per export: the largest integer width and height among normal evaluated rectangles at keyframe times. The patch origin follows the current rectangle, clamped to the source bounds. Blur samples this patch, while a separate alpha mask limits its visible footprint to the evaluated rectangle. Each alpha mask comes from an independent finite color source. Keeping it independent avoids expensive FFmpeg teardown through nested source splits. Rectangle commands sit immediately before their consuming filter branch and are bounded to 900 frames and 8 MiB aggregate per chunk. Keyframes do not create additional video processes. One-pixel-wide or one-pixel-high blur patches internally duplicate their sole column or row before `gblur` and crop back afterward. This avoids the bundled filter's width-one crash and height-one invalid blur output while preserving edge extension and source coverage.

Run `cargo test -p screenrecord-render tracking::tracked -- --nocapture --test-threads=1` with `SCREENRECORD_FFMPEG` pointing to the bundled runtime. Generated media checks every solid-mask pixel, fractional keyframes, exact tracked-blur agreement with an independent static filter reference, chunk restarts, loss across cuts with crop/zoom, review enforcement, cancellation, source immutability, and 1xN/Nx1/1x1 static and tracked masks. Run `cargo test -p screenrecord-render measure_tracked_blur -- --ignored --nocapture --test-threads=1` for the bounded 1080p export and 16-mask filter workload.

On this development machine with the bundled LGPL runtime and debug Rust orchestration, a 10-second 1920x1080 30-fps export with one tracked blur took 11.7762 seconds using NVIDIA H.264. Its 91 keyframes stayed in one video chunk, used a 301x216 patch, and wrote 29,038 command bytes. A separate 16-mask, 60-frame (two-second) filter workload with one filter thread and null output took 11.6061 seconds. The earlier nested alpha-source topology took 99.9838 seconds for a single 16-mask frame; the independent source version took 0.3534 seconds for that same single-frame workload. The latter comparison measures graph and frame processing plus teardown, not complete export throughput. These are synthetic workloads, not hardware coverage or a guaranteed export speed.

Subtitles are rendered with libass after webcam composition. The font is Segoe UI, with font size and 8-pixel background padding scaled from a 1080-pixel short edge. Text is centered with 5% side margins and a 48-reference-pixel top/bottom margin. The selected background is opaque. Libass handles wrapping and script shaping. Each chunk loads only its intersecting cues, snapped to the output frame grid. Literal braces are escaped and literal backslashes separated from following characters with a word joiner, following [libass's literal-brace support](https://github.com/libass/libass/wiki/Libass%27-ASS-Extensions) and [FFmpeg's ASS escaping](https://ffmpeg.org/doxygen/8.1/ass_8c_source.html).

Preview uses a transparent PNG on the canonical 1080p canvas. The caller supplies unsaved cue/style edits and scales the whole image, preserving export font metrics and wrapping. Jobs have a 30-second timeout and an owned temporary directory removed on cancellation or failure. Callers should cache results and bound concurrent jobs.

## Click indicators

The renderer reads button-down transitions from the original cursor samples. Left uses one amber ring, right uses two cyan rings, and legacy or middle-button events use one neutral ring. Each type shows its latest pulse. Releasing the button lets the pulse finish. A subsequent invisible sample ends it immediately, including at a recording-part boundary. Auto zoom uses the same events and groups simultaneous presses at one timestamp.

A pulse lasts 0.4 seconds. Its radius is `(12 + 16 * age / 0.4) * cursorSize * referenceScale`, with opacity `0.95 * (1 - age / 0.4)`. The colored stroke is 2.5 reference pixels wide, over a 4.5-pixel dark `#20242B` backing at the same opacity. The right-click inner radius is 0.64 of the outer radius. Raw event coordinates are projected through the current crop/zoom/reframe viewport independently of pointer smoothing. The center must remain inside that viewport, and the event must belong to the current retained interval. Events removed by trim or cuts do not continue into the next interval.

The renderer writes bounded libass vector drawings for active output frames, before the pointer and rounded screen mask, after the redacted source/background split. Camera and captions remain above them. This clips rings to the rounded screen pane and prevents them from coloring the blurred background. Camera-only, hidden cursor and hidden click indicators omit the layer. A project without click events adds no filter. Sparse recordings skip entire inactive chunks using indexed event bounds and calculate a second viewport only on frames with active pulses. Half-open frame gates and centisecond floors preserve supported 30/60 fps boundaries.

One existing 900-frame chunk uses at most three pulse channels and six vector passes per frame, with a 4 MiB ASS-file limit and cancellation checks during generation. A worst-case 4K/cursor-size-4 fixture with all three buttons repeatedly pressed produced 5,394 passes and 2,532,142 bytes, below that limit. It creates no per-click process, video input, or full-frame temporary image. Standard and WhatsApp exports share this path.

Run `cargo test -p screenrecord-render click --locked -- --nocapture --test-threads=1` with the bundled runtime. The tests decode Standard 30/60 fps and WhatsApp output and check ring timing, position, color and clipping through cuts, chunk boundaries, zoom, split layout and background blur. They also exercise cancellation and the maximum overlay file size. The `auto_zoom_uses_button_edges` test checks grouping of simultaneous presses.

Drawings use a nonnegative local origin before libass center alignment. A negative origin shifted the ring up and left by its radius. Checking pixels in all four quadrants and measuring the center reproduced a 17.5 px error. After the correction, the largest measured axis error across left, right and neutral rings at the reference cursor size was 0.14 px. Across sizes 0.5 and 4, the largest measured error was 1.33 px on a small, fading ring. Evidence is in `artifacts/clicks-0.5.2/render-centroid-before-fix.log`, `render-centroid-after-fix.log` and `render-centroid-size-fade.log`.

## Compact WhatsApp export

`ExportPreset::Whatsapp` creates a local H.264/yuv420p MP4 at 30 fps with faststart and, when audio is present, 48 kHz stereo AAC at 96 kbps. It does not send or upload the file. The 16,000,000-byte limit is this application's chosen target, not a statement of WhatsApp's upload limits. Standard export keeps its existing resolution, frame rate, encoder quality settings and 192 kbps AAC.

Core calculates the plan from retained duration rounded onto the 30 fps output grid. It reserves 10% plus 64 KiB for bitrate variation and container overhead, and reserves 96 kbps audio even for silent projects. Video bitrate is 320 kbps to 2.4 Mbps. The selected canvas aspect is preserved with even dimensions: maximum short/long edges are 720/1280, 480/854 or 360/640, chosen by bitrate. Very long clips that cannot meet the bitrate floor and canvases narrower than 64 pixels are rejected before encoding. Padding, radii, captions and blur use the actual short edge as their reference scale.

The renderer probes the actual geometry and bitrate settings before selecting an encoder. NVIDIA and AMD use their CBR modes; Intel uses equal target/max rates with lookahead disabled; Media Foundation uses its CBR rate control. [FFmpeg's Media Foundation encoder](https://github.com/FFmpeg/FFmpeg/blob/n8.1.1/libavcodec/mfenc.c) forwards mean/max bitrate and buffer size to the platform codec. These are rate-control requests. The measured final file size decides whether publication is allowed.

An oversized candidate gets at most one size-related retry. The renderer reduces video bitrate proportionally with additional reserve, clamps it to the 320 kbps floor, and keeps the original dimensions. Every video chunk is re-encoded with the same encoder/rate for that attempt. It reuses the prepared PCM mix, including ducking state across cuts, and remuxes AAC. It never truncates with `-fs`. If the retry still exceeds the cap, the operation removes its temporary output and asks the user to shorten the video or choose Standard. Hardware fallback remains limited to classified encoder failures; each fallback replaces every video chunk before muxing.

Both candidates undergo the existing complete frame-count, geometry, timing and audio contract checks, plus yuv420p and actual byte-size checks. The successful file is flushed and published without replacing another file. Only the completed progress event includes `outputBytes`; running progress stays monotonic through size retries and hardware fallback. Cancellation during retry removes owned temporary media and preserves a competing destination file.

Run `cargo test -p screenrecord-render whatsapp --locked -- --nocapture --test-threads=1` with `SCREENRECORD_FFMPEG` set to the bundled runtime. The generated-media cases decode landscape, portrait and square outputs, inspect MP4 atom order, compare the same project in Standard/WhatsApp, check cuts and tracked-mask privacy with moving framing and blurred backgrounds, and exercise retry success, floor failure, cancellation and publication races. The successful forced retry compares every decoded AAC sample with the first candidate. Test-only size caps exercise the production size-check path without creating a long test video.

In `artifacts/perf-0.5.1/render-whatsapp-focused.log`, the same 2.4-second generated project produced a 2,384,558-byte Standard file and an 879,325-byte compact file. A software-MF candidate of 870,473 bytes was retried against an injected 826,949-byte cap and finished at 782,409 bytes with identical decoded AAC. ## Failure and cancellation

Subprocess diagnostics retain only their final 16 KiB. Encoder probes have eight-second deadlines; media probing has a twenty-second deadline. The encoder deadline advances only when timestamps, frame counts, output sizes, or actual Windows process writes advance. Pipe-output byte counts are subtracted from process writes, so repeated progress messages cannot keep a stalled process alive. File writes during MP4 faststart count as work even after timestamps stop. Three minutes without work stops the process. Cancellation kills and reaps the owned subprocess before deleting its temporary files. Each Windows subprocess is assigned a kill-on-close job so it cannot remain orphaned after an application crash.

The ducking stream watchdog advances only as PCM frames are consumed. Consumer errors stop the decoder immediately; cancellation interrupts a blocked pipe read by terminating the decoder. Tests exercise both paths with owned child processes. As with other synchronous filesystem writes, a kernel-level blocked disk write cannot be forcibly interrupted by the Rust cancellation flag.

Temporary data is written inside a randomly named directory in the destination folder. Video chunks coexist with the final MP4 during muxing, so allow approximately twice the video output size as free space. The completed video is flushed and published with `tempfile::TempPath::persist_noclobber`, which uses a no-replace Windows rename. Existing outputs, including a file created by another process during export, are preserved.

Before publication, video frame count, dimensions, rate, and container duration are checked. Exports with audio must contain exactly one 48 kHz stereo AAC stream starting at zero and covering the edited duration within one [1024-sample AAC packet](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/aacenc.c#L1125). Muted exports must contain no audio stream. A generated two-second H.264 file with only 0.1 seconds of AAC exercises the case where a complete video hides truncated audio from the container duration check.

## Verification

Run `cargo test -p screenrecord-render`. Set `SCREENRECORD_FFMPEG` to the bundled runtime for all media tests. Existing integration tests also accept FFmpeg on PATH. Missing-runtime tests print an explicit skipped message. Windows fixture creation uses Media Foundation and works with the bundled LGPL runtime. Tests verify actual decoded pixels for camera placement, zoom, and pointer redraw; H.264 dimensions and audio; trim duration; portrait/square canvases; cancellation; and output publication races. Chunk tests compare every decoded frame and audio sample against a single-chunk export, including non-aligned trim and a webcam with a different frame rate.

Run the ignored `measure_bounded_motion_scheduler_scaling` and `measure_full_export_scaling_and_motion_bounds` tests explicitly with `--ignored --nocapture` to measure command scheduling and complete 1080p exports separately. The latter also decodes every result and observes the largest command file during export.

The generated-media editor tests verify 48 kHz PCM clip offset/fades/overlap and limiter headroom, exact privacy-region activation and unchanged outside pixels, transparent subtitle PNG geometry and literal Unicode text, and combined music/subtitle/privacy exports with crop, zoom, and webcam across forced 12-frame chunks. They compare decoded video/audio, fully decode the MP4, and verify source bytes remain unchanged. They do not use a physical capture device or native UI automation.

Stage 1 cut tests run with `cargo test -p screenrecord-render chunk_tests::cuts -- --nocapture --test-threads=1`. On the bundled LGPL runtime, three non-frame-aligned retained spans yielded 83 frames and 65,760 audio samples, with maximum per-frame RGB mean absolute error 0.2818 against the original-time reference and decoded AAC sample RMSE 0.001023 against independently sliced PCM. Adjacent split produced identical decoded AAC and a 0.0389 mean RGB difference from repeated hardware encoding. All five original file SHA-256 hashes were unchanged. A separate encoded red-frame sentinel test confirmed that four retained blue frames at `[2.017,2.120)` never included the deleted red screen frame or offset webcam frame. Cancellation after PCM preparation preserved an existing output and removed temporary media.

Measured results from the development machine are recorded in `artifacts/render-hardening-benchmark.json`: the 38,400-frame isolated scheduler took 59.6915 seconds with a global command file and 4.7013 seconds with bounded chunks. After timestamp, watchdog, and encoder-probe changes, a complete 60-second 1080p60 export took 53.6567 seconds with debug Rust orchestration. These measure different workloads; the scheduler ratio is not an end-to-end export speedup.
